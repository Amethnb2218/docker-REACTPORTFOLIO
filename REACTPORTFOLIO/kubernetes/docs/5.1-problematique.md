# 5.1 Problematique - Pourquoi Kubernetes ?

## Limites de Docker seul

Avec Docker Compose, notre projet fil rouge (React + Express + MongoDB) fonctionne sur une seule machine. Mais en production, plusieurs problemes apparaissent :

### 1. Pas de haute disponibilite
- Si le serveur tombe, toute l'application est indisponible
- Un conteneur qui crash n'est pas automatiquement relance
- Aucun mecanisme de self-healing

### 2. Pas de scalabilite horizontale
- Docker Compose ne permet pas de scaler intelligemment
- `docker compose scale` est basique (pas de load balancing integre)
- Impossible de scaler en fonction de la charge CPU/memoire

### 3. Gestion complexe multi-noeuds
- Comment deployer sur plusieurs serveurs ?
- Comment distribuer la charge entre les machines ?
- Comment gerer la communication inter-noeuds ?

### 4. Mises a jour risquees
- Pas de rolling update natif
- Rollback manuel et complexe
- Temps d'arret lors des deploiements

### 5. Gestion des secrets et configuration
- Variables d'environnement en clair dans docker-compose.yml
- Pas de rotation automatique des secrets
- Pas de separation config/code standardisee

## Ce que Kubernetes resout

| Probleme Docker | Solution Kubernetes |
|----------------|-------------------|
| Conteneur crash | Auto-restart, self-healing |
| Scalabilite | HPA (Horizontal Pod Autoscaler) |
| Haute disponibilite | ReplicaSets, multi-noeuds |
| Mise a jour | Rolling updates, rollback automatique |
| Secrets | Objets Secret chiffres, rotation |
| Reseau | Services, Ingress, DNS interne |
| Stockage | PersistentVolumes, StorageClasses |

## Dans notre projet

Notre portfolio necessite Kubernetes pour :
- **Frontend** : 2+ replicas avec load balancing pour gerer le trafic
- **Backend** : Auto-scaling selon la charge API
- **MongoDB** : StatefulSet pour la persistance des donnees
- **Zero downtime** : Rolling updates lors des nouveaux deploiements
