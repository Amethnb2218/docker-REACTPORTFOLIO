# 5.3 Concepts Kubernetes

## Node

Un **Node** est une machine (physique ou virtuelle) dans le cluster.

- **Master Node (Control Plane)** : gere le cluster (API Server, Scheduler, Controller Manager, etcd)
- **Worker Node** : execute les conteneurs (kubelet, kube-proxy, container runtime)

```
Cluster
├── Master Node (Control Plane)
│   ├── API Server
│   ├── Scheduler
│   ├── Controller Manager
│   └── etcd (base de donnees)
└── Worker Nodes
    ├── Node 1 (kubelet + pods)
    ├── Node 2 (kubelet + pods)
    └── Node 3 (kubelet + pods)
```

## Pod

Le **Pod** est la plus petite unite deployable dans Kubernetes.

- Contient un ou plusieurs conteneurs partageant le meme reseau et stockage
- Chaque pod a sa propre adresse IP
- Les conteneurs dans un pod communiquent via localhost
- Ephemere : peut etre detruit et recree a tout moment

```yaml
# Exemple : pod backend de notre projet
apiVersion: v1
kind: Pod
metadata:
  name: backend-pod
  labels:
    app: backend
spec:
  containers:
    - name: backend
      image: portfolio-backend:latest
      ports:
        - containerPort: 5000
```

## ReplicaSet

Un **ReplicaSet** garantit qu'un nombre specifie de replicas de pods fonctionnent a tout moment.

- Maintient le nombre desire de pods
- Recree les pods en cas de crash
- Rarement utilise directement (on utilise un Deployment)

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: backend-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
        - name: backend
          image: portfolio-backend:latest
```

## Deployment

Un **Deployment** gere les ReplicaSets et fournit les mises a jour declaratives.

- Cree et gere un ReplicaSet
- Permet les rolling updates
- Historique des revisions pour rollback
- C'est l'objet qu'on utilise pour deployer des applications stateless

```yaml
# Dans notre projet : backend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: portfolio
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
        - name: backend
          image: portfolio-backend:latest
          ports:
            - containerPort: 5000
```

## Service

Un **Service** expose un ensemble de pods comme un service reseau stable.

Types de services :
- **ClusterIP** (defaut) : accessible uniquement dans le cluster
- **NodePort** : expose sur un port de chaque noeud (30000-32767)
- **LoadBalancer** : cree un load balancer externe (cloud)
- **ExternalName** : mappe vers un DNS externe

```yaml
# Service backend de notre projet
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  selector:
    app: backend
  ports:
    - port: 5000
      targetPort: 5000
  type: ClusterIP
```

## Ingress

Un **Ingress** gere l'acces HTTP/HTTPS externe vers les services du cluster.

- Routage base sur le hostname ou le path
- Terminaison TLS/SSL
- Load balancing L7
- Necessite un Ingress Controller (nginx, traefik, etc.)

```yaml
# Dans notre projet : ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: portfolio-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: portfolio.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 5000
```

## Gateway API

La **Gateway API** est le successeur d'Ingress, plus expressif et extensible.

- Separation des roles : infra (Gateway) vs dev (HTTPRoute)
- Support natif TCP/UDP/TLS
- Routage avance (headers, weights, mirrors)

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: portfolio-gateway
spec:
  gatewayClassName: nginx
  listeners:
    - name: http
      port: 80
      protocol: HTTP
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: portfolio-routes
spec:
  parentRefs:
    - name: portfolio-gateway
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api
      backendRefs:
        - name: backend-service
          port: 5000
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: frontend-service
          port: 80
```

## ConfigMap

Un **ConfigMap** stocke des donnees de configuration non-sensibles sous forme de paires cle-valeur.

- Decoupler la configuration du code
- Peut etre montee comme volume ou injectee en variable d'env

```yaml
# Dans notre projet : configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: portfolio-config
data:
  PORT: "5000"
  USE_MEMORY_DB: "false"
  NODE_ENV: "production"
```

## Secret

Un **Secret** stocke des donnees sensibles (mots de passe, tokens, cles).

- Encode en base64 (pas chiffre par defaut)
- Peut etre chiffre avec EncryptionConfiguration
- Limite l'acces via RBAC

```yaml
# Dans notre projet : secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: portfolio-secret
type: Opaque
data:
  MONGO_URI: bW9uZ29kYjovL21vbmdvLXNlcnZpY2U6MjcwMTcvcG9ydGZvbGlv
```

## Volumes

Kubernetes propose plusieurs types de volumes pour la persistance :

- **emptyDir** : temporaire, lie au pod
- **hostPath** : repertoire de l'hote
- **PersistentVolume (PV)** : stockage provisionne par l'admin
- **PersistentVolumeClaim (PVC)** : demande de stockage par un pod
- **StorageClass** : provisionnement dynamique

```yaml
# PVC pour MongoDB dans notre projet
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mongo-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi
```

## StatefulSet

Un **StatefulSet** gere les applications stateful (bases de donnees, queues).

Differences avec un Deployment :
- Identite reseau stable (mongo-0, mongo-1, ...)
- Stockage persistant par pod
- Deploiement et scaling ordonnes
- Suppression ordonnee (dernier cree = premier supprime)

```yaml
# MongoDB dans notre projet : mongo-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo
spec:
  serviceName: mongo-service
  replicas: 1
  selector:
    matchLabels:
      app: mongo
  template:
    spec:
      containers:
        - name: mongo
          image: mongo:7
          volumeMounts:
            - name: mongo-data
              mountPath: /data/db
  volumeClaimTemplates:
    - metadata:
        name: mongo-data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 2Gi
```
