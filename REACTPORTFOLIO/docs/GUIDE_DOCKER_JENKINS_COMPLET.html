2. Definitions Docker essentielles

Docker

Docker est une plateforme qui permet d'emballer une application avec tout ce dont elle a besoin pour fonctionner : systeme minimal, dependances, fichiers, variables et commande de demarrage.

Dockerfile

Un Dockerfile est une recette. Il explique comment construire une image. Il contient des instructions comme FROM, WORKDIR, COPY, RUN, ENV, EXPOSE et CMD.

Image Docker

Une image est le resultat construit a partir d'un Dockerfile ou telecharge depuis un registre comme Docker Hub. Elle est immuable : elle sert de modele.

Conteneur

Un conteneur est une image en cours d'execution. Si l'image est le modele, le conteneur est l'instance vivante.

Docker Compose

Docker Compose permet de declarer plusieurs conteneurs dans un seul fichier YAML. Dans ton projet, Compose lance le frontend, le backend et MongoDB, puis les place sur le meme reseau.

Docker Hub

Docker Hub est un registre public d'images. Par exemple, mongo:7, node:20-slim, node:20-alpine et nginx:alpine viennent de Docker Hub si elles ne sont pas deja presentes localement.

3. Relation Dockerfile, image, conteneur et Docker Hub

Dockerfile local -> docker build -> image personnalisee -> docker run -> conteneur en execution

Pour obtenir un conteneur, il faut toujours une image. Mais pour obtenir une image, il y a deux possibilites :

CasExempleExplication
Image construite localement build: ./reactportfolio Docker lit le Dockerfile du dossier et construit une image frontend.
Image recuperee depuis Docker Hub image: mongo:7 Docker telecharge l'image officielle MongoDB. Tu n'as pas besoin d'ecrire un Dockerfile MongoDB.
La base de donnees a bien une image. Elle n'a simplement pas de Dockerfile dans ton projet parce que l'image officielle mongo:7 existe deja.

4. Explication de npm ci

Dans les deux Dockerfiles, on trouve : 

COPY package.json package-lock.json ./
RUN npm ci

npm ci installe les dependances Node.js de facon propre, stricte et reproductible. Il lit package-lock.json et installe exactement les versions indiquees.

ElementUtilite
package.jsonListe les dependances directes et les scripts du projet.
package-lock.jsonVerrouille les versions exactes de toutes les dependances.
npm ciInstalle exactement ce qui est dans le lock file, sans le modifier.
node_modulesDossier genere contenant les dependances installees.

Difference entre npm install et npm ci

CommandeComportementQuand l'utiliser
npm install Installe les dependances et peut modifier package-lock.json. Pratique en developpement quand tu ajoutes ou modifies des dependances.
npm ci Supprime node_modules s'il existe, puis reinstalle exactement les versions du lock file. Ideal pour Docker, Jenkins et les builds automatiques.

Dans Docker, on prefere npm ci car l'objectif est de construire la meme image sur toutes les machines. Cela evite les surprises entre ton PC, Jenkins et un serveur de production.

5. Explication des ports

Un port est une porte reseau. Une application ecoute sur un port pour recevoir des connexions. Dans Docker, il faut distinguer le port de la machine et le port du conteneur. 

ports:
  - "PORT_MACHINE:PORT_CONTENEUR"
ServicePort machinePort conteneurUtilite
Frontend300080Le navigateur ouvre http://localhost:3000, Docker redirige vers Nginx.
Backend50005000L'API Express est accessible sur http://localhost:5000.
MongoDB2701727017MongoDB Compass peut se connecter a mongodb://localhost:27017.
Jenkins80808080Interface web Jenkins.
Agents Jenkins5000050000Communication entre Jenkins et ses agents.
Regle importante : depuis ta machine, on utilise localhost. Entre conteneurs, on utilise les noms Docker : portfolio-backend, backend, mongo, selon la configuration du reseau.
Depuis ta machine : localhost:3000 -> frontend:80 localhost:5000 -> backend:5000 localhost:27017 -> mongo:27017 Depuis les conteneurs : frontend -> portfolio-backend:5000 backend -> mongo:27017

6. Dockerfile backend Express

FROM node:20-slim

WORKDIR /app

COPY package.json package-lock.json ./

RUN npm ci

COPY app.js ./
COPY src/ ./src/

ENV USE_MEMORY_DB=true
ENV PORT=5000

EXPOSE 5000

CMD ["node", "app.js"]
LigneExplication
FROM node:20-slimPoint de depart de l'image. Elle contient Node.js 20 dans une version Linux allegee. Le backend a besoin de Node pour executer app.js.
WORKDIR /appCree et utilise le dossier /app dans le conteneur. Les commandes suivantes s'executent dans ce dossier.
COPY package.json package-lock.json ./Copie les fichiers de dependances avant le code. Docker peut ainsi reutiliser le cache si le code change mais pas les dependances.
RUN npm ciInstalle les dependances backend : Express, CORS, Mongoose, dotenv, mongodb-memory-server, etc.
COPY app.js ./Copie le point d'entree de l'API Express.
COPY src/ ./src/Copie le dossier contenant les routes et le modele MongoDB.
ENV USE_MEMORY_DB=trueValeur par defaut : utiliser MongoDB en memoire. Dans Compose et Jenkins, cette valeur est remplacee par false.
ENV PORT=5000Definit le port par defaut de l'application Express.
EXPOSE 5000Documente que le conteneur ecoute sur le port 5000. Ne publie pas le port tout seul.
CMD ["node", "app.js"]Commande lancee quand le conteneur demarre. Si cette commande s'arrete, le conteneur s'arrete.

Lien avec app.js

const PORT = process.env.PORT || 5000
...
const useMemoryDB = process.env.USE_MEMORY_DB === 'true'
...
const mongoUri = process.env.MONGO_URI || 'mongodb://localhost:27017/portfolio'
...
app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`)
})

Le backend lit les variables d'environnement. Si USE_MEMORY_DB=true, il lance une base temporaire avec mongodb-memory-server. Si USE_MEMORY_DB=false, il utilise MONGO_URI pour se connecter au vrai conteneur MongoDB.

7. Dockerfile frontend React

FROM node:20-alpine AS build

WORKDIR /app

COPY package.json package-lock.json ./

RUN npm ci

COPY index.html vite.config.js styles.css ./
COPY src/ ./src/
COPY assets/ ./assets/

RUN npm run build

FROM nginx:alpine

COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]

Pourquoi deux FROM ?

Ce Dockerfile utilise un build multi-stage. La premiere image, Node.js, sert uniquement a compiler React. La deuxieme image, Nginx, sert uniquement a executer le site en production.

LigneExplication
FROM node:20-alpine AS buildDemarre une etape de construction nommee build. Node est necessaire pour executer Vite.
WORKDIR /appDossier de travail dans l'etape Node.
COPY package.json package-lock.json ./Copie les fichiers qui definissent les dependances frontend.
RUN npm ciInstalle React, Vite, React Router, Framer Motion et les autres dependances.
COPY index.html vite.config.js styles.css ./Copie le HTML racine, la configuration Vite et le CSS global.
COPY src/ ./src/Copie les composants et pages React.
COPY assets/ ./assets/Copie les images et ressources utilisees par le frontend.
RUN npm run buildExecute vite build. Cela genere le dossier dist.
FROM nginx:alpineNouvelle image finale plus legere. Elle ne contient pas Node ni le code source complet.
COPY --from=build /app/dist /usr/share/nginx/htmlCopie uniquement le resultat compile dans le dossier servi par Nginx.
COPY nginx.conf /etc/nginx/conf.d/default.confInstalle la configuration Nginx du projet.
EXPOSE 80Indique que Nginx ecoute sur le port 80 dans le conteneur.
CMD ["nginx", "-g", "daemon off;"]Lance Nginx au premier plan. daemon off evite que le conteneur s'arrete immediatement.

8. Le dossier dist

Le dossier dist est genere par Vite quand tu executes npm run build. Ce n'est pas le code source React. C'est le resultat final optimise pour le navigateur.

Element dans distRole
dist/index.htmlPage HTML principale envoyee au navigateur.
dist/assets/*.jsJavaScript compile et optimise. Il contient le code React transforme en code executable par le navigateur.
dist/assets/*.cssCSS final minifie.
dist/assets/*image*Images optimisees et renommees avec un hash pour le cache navigateur.

Dans le Dockerfile frontend, seul dist est copie dans l'image finale Nginx. Cela rend l'image finale plus petite et plus propre.

10. MongoDB, image Docker Hub et volume

MongoDB n'a pas de Dockerfile local parce que ton projet n'a pas besoin de construire MongoDB. Il utilise une image officielle deja prete : 

image: mongo:7

Si l'image mongo:7 n'existe pas localement, Docker la recupere automatiquement depuis Docker Hub.

Pourquoi le volume est important

volumes:
  - mongo-data:/data/db

MongoDB stocke ses donnees dans /data/db. Le volume mongo-data garde ces donnees en dehors du cycle de vie du conteneur. Tu peux supprimer et recréer le conteneur MongoDB sans perdre les donnees tant que le volume existe.

CommandeEffet
docker compose downSupprime les conteneurs, mais garde le volume.
docker compose down -vSupprime les conteneurs et les volumes. Les donnees MongoDB sont supprimees.

11. Configuration Nginx

resolver 127.0.0.11 valid=10s;

server {
    listen 80;
    server_name localhost;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api {
        set $backend_url http://portfolio-backend:5000;
        proxy_pass $backend_url;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_cache_bypass $http_upgrade;
    }
}
LigneUtilite
resolver 127.0.0.11 valid=10s;Utilise le DNS interne de Docker. Cela aide Nginx a resoudre les noms de conteneurs sur le reseau Docker.
listen 80;Nginx ecoute sur le port 80 dans le conteneur.
server_name localhost;Nom symbolique du serveur Nginx.
root /usr/share/nginx/html;Dossier ou se trouvent les fichiers React compiles.
index index.html;Fichier par defaut servi au navigateur.
location /Regle pour toutes les pages frontend.
try_files $uri $uri/ /index.html;Si l'URL ne correspond pas a un fichier physique, Nginx renvoie index.html. C'est necessaire pour une SPA React.
location /apiRegle speciale pour les appels API.
set $backend_url http://portfolio-backend:5000;Definit l'adresse du backend dans le reseau Docker.
proxy_pass $backend_url;Transfere la requete API vers Express.
proxy_http_version 1.1Utilise HTTP/1.1 pour le proxy.
proxy_set_header Host $hostTransmet l'hote original au backend.
proxy_cache_bypass $http_upgradeEvite certains problemes de cache avec les connexions speciales.
Quand le navigateur appelle /api/projects depuis le frontend, Nginx intercepte /api et transmet la requete au backend Express.

13. Jenkinsfile ligne par ligne

Le Jenkinsfile decrit le pipeline CI/CD. Jenkins lit ce fichier depuis GitHub, puis execute les etapes dans l'ordre.

Structure globale

pipeline {
    agent any
    environment { ... }
    triggers { ... }
    stages { ... }
    post { ... }
}
ElementUtilite
pipeline {}Declare un pipeline Jenkins declaratif.
agent anyJenkins peut executer ce pipeline sur n'importe quel agent disponible.
environment {}Definit des variables globales reutilisables dans les etapes.
triggers {}Definit ce qui declenche automatiquement le pipeline.
stages {}Contient les grandes etapes : checkout, install, tests, build, deploy.
post {}Actions executees apres le pipeline : succes, echec, nettoyage.

Variables d'environnement Jenkins

environment {
    FRONTEND_DIR = 'REACTPORTFOLIO/reactportfolio'
    BACKEND_DIR = 'REACTPORTFOLIO/EXPRESSJS PORTFOLIO'
    EMAIL_RECIPIENTS = 'mouhamed.sall@email.com'
}
VariableUtilite
FRONTEND_DIRChemin du frontend dans le workspace Jenkins.
BACKEND_DIRChemin du backend. Les guillemets sont importants car le dossier contient un espace.
EMAIL_RECIPIENTSAdresse qui recevra les notifications de succes ou d'echec.

Declencheur GitHub

triggers {
    githubPush()
}

Cette instruction indique que Jenkins peut lancer le pipeline quand GitHub envoie un evenement de push, si le webhook GitHub est configure.

Stage Checkout

stage('Checkout') {
    steps {
        echo 'Recuperation du code source...'
        checkout scm
    }
}
ElementUtilite
stage('Checkout')Nom visible dans Jenkins pour l'etape de recuperation du code.
steps {}Liste les actions de cette etape.
echoAffiche un message dans les logs Jenkins.
checkout scmRecupere le code depuis le depot Git configure dans le job Jenkins.

Stage Install Dependencies

stage('Install Dependencies') {
    parallel {
        stage('Frontend Dependencies') {
            steps {
                dir("${env.FRONTEND_DIR}") {

                }

Cette etape installe les dependances frontend et backend en parallele. Cela accelere le pipeline car les deux installations ne dependent pas l'une de l'autre.

dir("${env.BACKEND_DIR}")Entre dans le dossier backend avant d'executer la commande.

stage('Tests') {

Jenkins execute les tests backend. Dans ton package.json, npm test lance node --test.

stage('Deploy') {
    steps {

stage('Health Check') {
    steps {

Bloc post

post {
    success { ... mail ... }
    failure { ... stop/rm ... mail ... }
    always { cleanWs() }
}
BlocExplication
successExecute si tout le pipeline reussit. Envoie un email de succes.
failureExecute si une etape echoue. Arrete et supprime les conteneurs, puis envoie un email d'echec.
alwaysExecute quoi qu'il arrive. Nettoie le workspace Jenkins avec cleanWs().

14. Health checks et correction de l'erreur du pipeline

L'erreur vue dans les logs etait : 

Error response from daemon: container ... is not running

Cela signifie que Jenkins avait cree le conteneur frontend, mais que celui-ci s'etait arrete avant la verification.

Pourquoi un conteneur peut s'arreter ?

Un conteneur reste vivant tant que son processus principal reste vivant. Pour le frontend, le processus principal est Nginx : 

CMD ["nginx", "-g", "daemon off;"]

Si Nginx ne parvient pas a charger correctement sa configuration ou a resoudre son upstream backend, il peut quitter, et le conteneur s'arrete.

Les corrections importantes

CorrectionPourquoi
--network-alias mongoPermet au backend de trouver MongoDB avec le nom mongo.
--network-alias backendPermet aux autres conteneurs d'utiliser le nom backend.
resolver 127.0.0.11 dans NginxUtilise le DNS interne Docker.
127.0.0.1 au lieu de localhost dans les health checksEvite les problemes de resolution IPv6/IPv4 dans certains conteneurs.
sleep 5, sleep 3, sleep 10Laisse aux services le temps de demarrer avant les tests.
Important : les messages No such container au debut du deploy ne sont pas forcement graves, car les commandes ont || true. Jenkins les ignore volontairement pour permettre le premier deploiement.

16. Resume final

Dockerfile backend -> construit l'image portfolio-backend -> lance Express avec node app.js -> Express ecoute sur 5000 -> Express se connecte a mongo:27017 Dockerfile frontend -> construit React avec Node -> genere dist -> copie dist dans Nginx -> Nginx ecoute sur 80 -> machine expose le site sur localhost:3000 compose.yaml -> construit frontend et backend -> telecharge mongo:7 -> cree les conteneurs -> cree le reseau portfolio-net -> cree le volume mongo-data Jenkinsfile -> recupere le code -> installe les dependances -> lance les tests -> build le frontend -> construit les images Docker -> deploie les conteneurs -> verifie frontend et backend -> nettoie et envoie un email
